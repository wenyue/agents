# 编写规则

写出一条其他 Agent 不需要额外背景就能应用、前后一致且有证据支撑的完整规则。每次都要按用户当前
指定的范围重建完整要求，不要沿用旧改动留下的结构。

## 编写优先级

清晰、可执行、无歧义是验收条件。三项都满足后，再在不削弱它们的前提下尽量简洁。

每项要求都只能有一种明确解读。约束对象、适用范围、条件、强度和预期行为等信息，只要会影响含义，
就必须写明。使用可观察的判断条件和直接结果。如果缩短后会隐藏、合并或删除任何可能改变规则含义的
信息，就不能采用这个短版本。

除非有新证据或用户明确同意，不得扩大、缩小、弱化、强化或改写原意。

## 分类

动笔前，先根据规则的分发方式、职责归属和用户要的产物判断类型。

| 判断依据 | 类型 |
| --- | --- |
| 最终规则由一个仓库维护并直接执行 | 项目本地规则 |
| 发布出去的规则会直接约束不同仓库 | 共享规则 |
| 发布出去的内容负责写出一份由目标项目自己维护的完整规则 | 共享规则生成契约 |

删掉本地细节，并不会自动变成共享规则。只有规则本身在不同仓库中都能保持稳定，才把它归为共享规则；
否则继续作为项目本地规则。

## 证据

只查那些可能改变规则内容、归属、适用方式或验证方式的事实。

### 规则依据

确定目标结果、限制、示例、技术选择、阈值、兼容要求、强度、Scope、优先级和例外。检查这条规则负责的
整套规则、更通用和更具体的规则，以及实际用法。现有规则只用来核对证据和防止遗漏；变更历史、个人
偏好、可复用流程和其他地方管理的运行时事实不属于成品。

### 仓库事实

如果是项目本地规则，要核实应用规则所需的仓库事实和真正执行约束的位置；生成内容归属和模块边界会
影响规则时也要检查。写入具体说法前先找到证据。

### 分发与生成依据

发现或分发方式可能变化时，检查对应入口。如果是共享规则，检查有代表性的仓库，只保留能直接应用的
稳定要求、项目本地规则的优先级和允许的例外。如果是共享规则生成契约，定义目标项目必须收集的证据，
再检查有代表性的规则体系、优先级机制、生成入口和验证器。

## 编写

1. 定义完整规则：负责和不负责的要求、类型、强度、Scope、适用方式、优先级和例外。
2. 根据当前用户意图和已核实证据重新整理完整成品。保留用户要的结果和已核实的决定，包括阈值、
   技术选择和例外；删除过时、重复、冲突或放错位置的内容。假设今天从零开始写这条规则，按最合理的
   顺序组织它；每项要求都放到应在的位置，不要为了缩小 diff 而在末尾补一句，也不要机械保留旧顺序。
3. 每项要求都写进负责它的 Rule。用户点名的 Rule 不负责某项要求时，不要写进去。只有负责该要求的
   Rule 已经在用户请求范围内时，才能直接修改；否则先取得用户明确同意。
4. 只修改 Rule，以及让这些 Rule 正确加载或分发所必需的平台适配文件、索引、清单、语言镜像和契约
   测试。其他类型的改动都超出范围，必须报告。
5. 最终规则要按当前归属、条件和行为写成稳定状态下的契约。过渡工作放进实施计划；只有当前兼容或
   迁移仍然依赖某项过渡行为时才把它写进规则，并写明触发条件和退出条件。把评审历史转成当前判定
   规则：写明对象、选择结果的可观察属性和对应行为。
6. 只使用足以确定结果的最小一组正向判断条件。旧名称、旧位置、被淘汰的分类标准或实现，只有当前
   输入仍可能出现、Agent 确实需要区分时才保留。
7. 不看 diff，从头读完整成稿。先解决遗漏和冲突解读，再删除重复、历史和不能指导行动的说明。如果
   有多种做法都合理，就给执行 Agent 留出选择空间；如果顺序会影响正确性或安全性，就明确规定步骤。

只有当 Agent 需要某项事实、配置值或实现细节来决定或执行动作、解释证据、满足前置条件、处理失败或
报告结果时，才把它写进成品。以上用途都不需要这项信息时就省略；如果只需知道某个自动行为存在，而
不需要知道它的具体配置，只写这个行为。

纳入版本控制的规则只能写仓库相对路径或协议规定的稳定路径，不能写某台机器专用的绝对路径。每项要求
只能在一个地方维护；平台适配文件只保留平台必需的元数据，再加一个指向源文件的引用。

提到其他 Rule 或 Skill 时，使用目标系统声明或认可的正式名称，不要写它在文件系统里的路径。

根据规则类型确定内容边界：

- 项目本地规则要根据已经核实的仓库事实写清最终要求，并把相关要求、相互关系和例外放进负责它们的
  最具体规则；
- 共享规则只写跨仓库都成立的约束、不绑定具体实现的目标条件和协议规定的路径，具体实现和更窄的
  例外留给项目本地规则；
- 共享规则生成契约要把编写说明和最终规则分开，只规定目标项目要查哪些证据，不能凭空编造目标事实。

## 表达格式

根据每项要求要控制的行为选择最清楚的表达格式，不要把下面的名称和顺序变成每条规则都必须采用的
章节模板。

### 步骤与检查清单

只有规则生成契约中的编写顺序会影响结果时，才使用编号步骤（`1.`）。最终规则可以用 Markdown 任务
清单（`- [ ]`）列出需要一起查看、但没有先后依赖且可分别核验的政策要求。每一项都要写清对象、要求
的动作或属性以及可观察结果。默认格式为
`- [ ] 当<条件>时，<对象>必须<动作或属性>；确认<可观察结果>。`
无条件项目才省略条件。如果这些项目实际规定了多步执行流程，应把流程移到 Skill。

### 示例

只有示例能消除实质歧义时才添加。用最小而完整的输入/输出、修改前/修改后或边界对照，只说明一个
关键区别。强制契约的两侧使用粗体标签 `**必须**` 和 `**无效**`；允许例外的默认做法使用
`**推荐**` 和 `**避免**`。精确语法使用代码块，只对照行为时使用单行列表。所有要求都必须先写进
规范正文；示例不能新增或覆盖要求。

### 正面要求

优先使用足以确定结果的最小一组正面要求，默认句式为：
`当<可观察条件>时，<对象>必须<动作>；结果必须具备<可观察属性>。`
无条件要求才省略条件。输出格式要列明必填字段；条件规则要使用明确的 `如果` 或 `当`。

### 负面要求

只有某种可能出现的有害捷径没有被正面契约完整排除时，才写负面要求。默认句式为：
`当<可观察触发条件>成立时，不得<禁止动作>；应改为<要求的替代做法>。`
没有替代做法时，写明长期存在的正确性、安全或兼容性后果。不要写“绝不走捷径”“不得含糊”或“避免
不必要的工作”这类没有适用条件的禁令。

## 规则契约

### 基本格式

每条规则都必须这样开头：

```markdown
# Rule Title

Strength: `Mandatory|Default|Advisory`

Scope: One sentence naming the rule's owned responsibility.
```

只有规则负责的内容确实需要某个章节时才添加。

### 规则正文

范围更广的规则不能重复更具体规则的内容，也不能在不明说的情况下覆盖它。

根据适用范围组织正文：

- 项目本地规则必须包含 H1、Strength、Scope 和按职责组织的要求；只有已经核实的规则关系或例外需要
  表达时才添加 Boundaries 或 Exceptions；
- 共享规则必须包含 H1、Strength、Scope 和稳定约束；需要时添加 Boundaries 或 Precedence，并明确
  项目本地规则的优先级，但不要重复目标项目特有的要求。

### 生成契约

共享规则生成契约必须包含 Generation Contract、Evidence、Content 和 Boundaries。它要产出一份完整、
由目标项目自己维护的候选规则，不能把编写流程和最终项目要求混在一起。

## 验证

### 成品检查

- 从头阅读最终规则，不要只看改动行；确认分类、归属、强度、Scope、适用范围、优先级、例外和完整
  规则。
- 确认改动只限于 Rule 及其管理的文件和入口。
- 检查最终成稿是否存在歧义或语义偏移：每项要求必须只有一种明确解读；只有出现新证据或用户明确同意时，
  才能改变原意。任一条件不满足都不能通过。
- 任何要求只要不能根据已写出的上下文应用，或因压缩而变得不完整，就不能通过。
- 脱离 diff 和旧实现逐项阅读。每项否定式要求都要指出当前触发状态，以及长期存在的正确性、安全性或
  兼容性后果；缺少相应依据时，改为直接说明当前期望的行为和归属。
- 只有当前输入仍需要区分时，才保留备选名称、位置、分类标准、实现、对照、例外或理由。
- 对每项条件或对照做反事实检查：保持规则里的正向判断条件不变，只改变该条件；如果要求的结果不变，
  就删除这项条件或对照。
- 按职责检查各子节。通用要求放在公共内容中；有条件的要求放在负责它的主题下。
- 对照语言镜像的结构，确保路径、命令、标识符、代码块、分类、强度和行为没有走样。

### 适用环境检查

- 项目本地规则要在当前仓库里核对具体说法、执行位置、例外和规则之间的关系；
- 共享规则要选择有代表性的环境测试，覆盖项目本地规则的优先级、允许的覆盖方式，以及不依赖单个仓库
  细节的稳定要求；
- 共享规则生成契约要至少模拟生成一份完整的目标规则，并核对它的证据、内容和边界；如果声称能广泛
  移植，还要选择差异明显的多个目标。

### 加载入口检查

对每个必需的发现入口运行当前项目规定的验证器、契约测试和 diff 完整性检查。确认适用的平台适配文件、
索引、清单、语言镜像和其他分发入口仍然一致。

只要证据还有疑点、说法没有事实支持、必需的发现入口已经过时或无法访问，或者必需检查失败或没有报告，
就不能声称工作成功。

## 结果

交付时说明：产物属于哪一类、由哪个产物或仓库负责、最终文档结构、保留了哪些决定、删除或迁移了哪些
内容、更新了哪些发现入口、分发入口和语言镜像，以及各项验证的具体结果。

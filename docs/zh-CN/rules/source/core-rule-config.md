# 插件规则配置

强度：`Mandatory`

适用范围：规则强度、优先级、归属、激活、语义冲突和项目编号。

## 强度等级

- `Mandatory`：必须遵守，除非更高优先级的指令另有要求。
- `Default`：默认遵守；只有更高优先级的直接指令或按优先级元组排序更高的规则要求不同结果时，
  才可以调整。
- `Advisory`：可在有帮助时结合任务实际情况采用。

## 优先级

在系统、开发者和用户的直接指令之后，按以下顺序解决规则冲突：

1. 强度：`Mandatory` > `Default` > `Advisory`。
2. 相同强度时的归属：项目 > 插件。
3. 相同强度和归属时的具体程度：更窄的适用文件范围 > 更宽的适用文件范围 > 全局层级。`always` 和
   `harness` Rule 同属全局层级；Harness selector 只改变激活条件，不改变优先级。
4. 注册表顺序定义插件规则的确定性分发顺序，项目文件顺序定义项目规则的确定性分发顺序；
   两种顺序都不解决语义冲突。

低强度项目规则不得覆盖高强度插件规则。

## 激活

- `always` Rule 在每个受支持 Harness 的整个生命周期中生效。
- `file` Rule 由匹配路径激活，并按所属 delivery adapter 的契约在 session 内保持激活。
- `harness` Rule 只在匹配 Harness 的 session-context 生命周期中激活。不得据此为其他 Harness 生成
  原生 Rule wrapper。
- 只有 Harness 已具备真实 session-context delivery route 时，才能注册 `harness` Rule；生成原生 Rule
  wrapper 不算该 route。

## 语义冲突

- 不得在配置代码中尝试推断语义冲突。
- 声明冲突前先应用优先级元组。同一组已证实事实下，如果不存在能够同时满足两项要求的单一动作或
  结果，则这些要求不兼容。
- 不兼容要求在强度、归属和具体程度上仍然相同时，只进行确认冲突所需的只读调查，然后在任何
  副作用前停止。不得把分发顺序当成隐含胜者。
- 报告冲突规则的 ID、来源、强度、范围和不兼容要求，并请用户解决冲突。

## 规则归属

- 每份插件规则的政策只保留在 `rules/registry.json` 注册的一个源文件中。
- 每份项目规则的政策在 `.agents/rules/` 下只保留一个源文件。
- 各 Harness 的规则包装文件必须保持精简：可以包含 Harness 要求的元数据或运行时字段，
  再加一个指向所属规则的引用；所有政策都留在所属规则中。
- 由所属的 Harness 配置或 catalog 定义包装文件的路径、模板和生成行为，并将这些运行时事实保留在
  该 Harness 配置或 catalog 中。
- Harness-scoped Rule 可以将共享动作映射到一个 Harness 的原生工具、能力、生命周期语义、约束和
  能力缺失时的 fallback。它必须保持 plugin-private 且只描述执行机制；不得重新定义共享政策、用户
  授权或完成标准。

## 编号

| 范围 | 适用内容 |
| --- | --- |
| `00–09` | 项目规则：工具、约定、结构和实用工具。 |
| `10–19` | 模块规则：功能、界面和边界明确的子系统。 |
| `20–29` | 领域规则：测试及其他横切关注点。 |
| `30–39` | 包和项目插件规则。 |

插件规则使用描述性的 `core-*` 和 `file-*` ID，不使用数字名称。项目规则使用上述数字范围，
并遵循此插件拥有的上述优先级契约。

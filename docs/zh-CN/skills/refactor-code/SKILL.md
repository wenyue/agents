# 重构代码

重组一个具体目标，同时不改变其调用方或外部使用者能够观察到的内容。

## 判断框架

### 证据与保留边界

- 确定目标、结构问题、已批准范围和预期内部结果。
- 阅读适用的项目 Rule、目标代码、调用方、测试、相关历史和附近的既有模式。当 generated owner 和
  项目验证要求会影响目标时，查明它们。
- 在受支持的调用方 seam 定义**保留边界**：保持稳定的行为与外部契约，以及能够区分保留边界成立
  与回归的证据。为每项计划写入在已批准范围内确定 owner。

目标 identity、范围、ownership 或区分性证据尚未解决时停止，而不是将其视为臆造项目事实的许可。

### 结构判断

- 选择能够消除既定问题并使实现知识保持局部的最小且内在一致的内部结构。
- 保持调用方可见行为、外部契约和受支持的调用方 seam 稳定。只有已批准结果需要时，才添加
  framework、extension point、compatibility layer 或 test-only interface。
- 让测试位于受支持的调用方 seam。只有为了保留这些行为断言，才修改与已淘汰内部结构耦合的测试；
  只有当前证据表明不存在受支持路径依赖过时内部结构后，才删除它们。

### 相邻路由

- 如果请求的结果只是符号或文件重命名，在写入前停止，并将目标和范围交接给 `rename-code`。
- 如果请求是在代码库中寻找架构改进机会，在写入前停止，并将搜索范围交接给
  `improve-codebase-architecture`。
- 使用 `codebase-design` 选择 interface、seam、adapter 关系或测试表面；只有结果仍是内部且保持
  行为的改动时，才回到这里继续。
- 如果预期结果会改变公共 interface、持久化格式、协议、集成或用户可见行为，在写入前停止，并将
  已确认的设计或 specification 交接给 `implement`。

## 应用所选结构

只修改所选结构需要的已归属实现表面。迁移受影响的内部调用方，淘汰被取代的内部结构，并让每项
编辑都可追溯到已批准范围和保留证据。

## 验证岛

写出一个内在一致的内部结果后：

1. 将每个改动表面与已批准范围和保留边界对照。确认所选结构已完整完成、受影响的内部调用方已
   迁移，并且被取代的内部结构已移除。
2. 到达 completed-change checkpoint 后，通过当前项目的 verification owner 运行受影响表面的每项
   必需检查。如果没有声明该 owner，则从适用的项目 Rule 查明并运行必需检查。包含针对保留边界的
   聚焦证据。
3. 当改动表面对照或检查发现由当前证据唯一确定的修正时——包括范围外编辑、范围内回归、不完整的
   结构结果或遗留的过时内部结构——只有它在范围内且保持行为才应用，然后重新运行每项受影响检查。
   每次得到结果后返回判断；只有证据能够确定另一项受支持修正时，才继续。
4. 如果同一 finding 在修正后原样复现，或者提议的修正不会改变实现，则以 no-progress failure
   结束。保留有用的部分状态和已经获得的证据。

## 结束并交接

- 只有结构问题和过时内部结构都已消除、保留边界成立，并且所有必需检查均通过时，才为
  **Complete**。
- 当相邻路由适用，或者无法确定所需的目标、边界、范围、owner 或区分性证据时，**写前停止**。
  报告路由、确切缺失的决定或确切缺失的证据，并保持重构未启动。
- 当必需检查仍未成功、改动表面的 finding（包括不完整的已批准结果或过时内部结构）没有受支持的
  范围内修正、无法继续取得进展，或者证据已无法区分重构和回归时，**写后失败**。保留有用的部分
  状态，并报告确切失败以及下一个 owner 或决定。

写入后，failure 优先于同时出现的 stop。在 handoff 中包含该 stop 事实，同时不扩大范围或改变契约。

报告已消除的结构问题、保留的行为与契约、修改的内部表面、删除的过时代码、确切检查与退出状态、
执行过的修正或恢复，以及所有未解决或未测试的表面。

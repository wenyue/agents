# 编写代码注释

本 Judgment-led Skill 只有在项目约定要求注释，或注释能保留代码、名称、签名、类型和紧邻的控制流
尚未表达的信息时，才编写注释。

## Judgment Frame

根据请求、相关代码、适用的仓库规则和语言规则、附近仍在维护的注释、格式化或 lint 配置，以及生成
文件的所有权作出判断。以下事项由目标项目决定：

- 注释使用的语言和术语；
- 行注释、块注释和文档注释的语法；
- 标点、大小写、换行和 tag 约定；
- 声明应使用 doc comment、docstring、annotation，还是不加注释；
- `TODO`、抑制指令或 API 文档 tag 等必需标记。

项目约定优先于下述默认规则。如果无法确定生成目标的 source owner 或允许编辑的表面，则在修改前
停止。

确定如果没有注释，后来的读者会误解什么、违反什么约束，或不得不重新查明什么。有用的注释作用
包括：

- 调用方无法从签名推断的行为；
- 不变量和执行顺序约束；
- 生命周期、所有权、取消或并发要求；
- 边界情况、fallback 行为和预期失败模式；
- 选择不直观方案的理由，或不采用某个明显替代方案的原因；
- 外部协议、兼容性、安全性或产品要求。

真正的问题在于名称或结构时，应报告该问题；除非这项工作也已获授权，否则不要修改。

## 克制地编写

对于已授权的编辑，使用目标语言的语法和项目语气，以最小表述补足缺失信息，不要复述下一行代码。

当项目没有规定时：

- 与附近仍在维护的文档保持语言和术语一致。
- 公共声明使用该语言原生的文档形式；局部原因说明使用普通行注释或块注释。
- 使用主动、直接的表述，每条注释只表达一个意思。
- 说明性注释使用完整句子；标记、指令、代码片段和 URL 保持所要求的原生形式。
- 使用目标语言支持的文档语法引用参数、异常和符号。

有效标记、抑制指令、文档 tag、URL、代码片段和生成注释保持其必需形式。只有目标项目规则或请求
要求时才修改。

## 示例

**推荐**

```text
// Keep the old token until persistence succeeds so a failed write can be retried.
# The service reports healthy before the index is ready; poll the readiness endpoint instead.
```

**避免**

```text
// Increment the retry count.
# Return the cached value.
```

## 验证并报告

对于只读 review，不修改文件或结构，并且只运行只读检查。按位置报告可执行的缺失、误导、冗余或
过时注释，或报告未发现可执行问题。

对于编辑，运行项目声明的每项相关 formatter、文档检查、analyzer 或 linter，并报告在哪些位置
添加、修改或有意省略了注释，以及这些注释保留了哪些信息。若项目未声明相关检查，将结果标为
untested。若必需检查不可用或失败，报告它，并且不要声称成功完成。

两个分支都要列出每项检查，并明确区分 validated、untested 和 failed 结果。

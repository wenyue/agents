# 编写代码注释

除非项目约定要求添加注释，否则只有注释能够补充代码、名称、签名、类型或紧邻的控制流尚未表达的
信息时，才编写注释。

## 了解项目约定

编写前，阅读适用的仓库规则和语言规则、附近的注释、格式化或 lint 配置，以及生成文件的所有权。以下事项由目标项目决定：

- 注释使用的语言和术语；
- 行注释、块注释和文档注释的语法；
- 标点、大小写、换行和 tag 约定；
- 声明应使用 doc comment、docstring、annotation，还是不加注释；
- `TODO`、抑制指令或 API 文档 tag 等必需标记。

项目约定优先于非显然信息启发式和下述默认规则。如果目标看起来是生成文件，但无法确定其所有权或
允许编辑的表面，则在修改前停止，并报告继续所需的 generator 或 owner 证据。

## 决策流程

1. 确定请求是授权编辑，还是只要求审查。对于只读审查，检查注释及相关代码，报告可执行的缺失、误导、
   冗余或过时注释，仅运行只读检查，不修改文件或结构，然后报告审查结果。
2. 对于已授权的编辑，确定如果没有这条注释，后来的读者会误解什么、违反什么约束，或不得不重新查明
   什么。
3. 如果答案是“什么都不会”且项目约定不要求注释，则保持无注释。真正的问题在于名称或结构时，报告
   该问题；除非用户另行授权，否则不要修改名称或结构。
4. 确定注释的作用：API 契约、不变量、生命周期、边界情况、失败行为、设计理由、外部要求或局部意图。
5. 用尽可能短的表述补足缺失的信息。
6. 遵循目标语言的语法，以及项目的语气和格式规则。
7. 将代码与注释放在一起阅读，删去只是复述下一行代码的内容。
8. 运行项目声明的每项相关格式化、文档检查、静态分析或 lint。如果项目未声明相关检查，将结果报告为
   untested。如果必需检查不可用或失败，报告不可用或失败的检查，并且不要声称成功完成。

## 高价值内容

- 调用方无法从签名推断的行为；
- 不变量和执行顺序约束；
- 生命周期、所有权、取消或并发要求；
- 边界情况、fallback 行为和预期失败模式；
- 选择不直观方案的理由，或不采用某个明显替代方案的原因；
- 外部协议、兼容性、安全性或产品要求。

## 项目未作规定时的默认规则

- 与附近仍在维护的文档保持语言和术语一致。
- 公共声明使用该语言原生的文档形式；局部原因说明使用普通行注释或块注释。
- 使用主动、直接的表述，每条注释只表达一个意思。
- 说明性注释使用完整句子；标记、指令、代码片段和 URL 保持所要求的原生形式。
- 使用目标语言支持的文档语法引用参数、异常和符号。

## 示例

**推荐**

```text
// Keep the old token until persistence succeeds so a failed write can be retried.
# The service reports healthy before the index is ready; poll the readiness endpoint instead.
```

**避免**

```text
// Increment the retry count.
# Return the cached value.
```

## 保留特殊形式

有效标记、抑制指令、文档 tag、URL、代码片段和生成注释保持其必需形式。只有目标项目规则或用户
请求要求时才修改。

## 结果

对于只读审查，按位置报告 finding 和 omission，或报告未发现可执行问题，并列出运行或不可用的每项
只读检查。对于编辑，报告在哪些位置添加、修改或有意省略了注释，以及这些注释保留了哪些信息。两个
分支都要列出每项检查及其结果，并明确区分 validated、untested 和 failed 结果。

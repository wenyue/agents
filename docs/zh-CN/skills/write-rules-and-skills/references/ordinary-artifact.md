# 普通工件

普通工件（Ordinary Artifact）是直接作为政策或触发式工作使用的 Rule 或 Skill。本 reference
负责其生命周期分类、运行边界和代表性应用。

## 划分 owner 边界

| 证据 | 类别 | 契约 |
| --- | --- | --- |
| 一个仓库拥有并直接使用完整政策或工作 | 项目级 | 根据已验证的仓库事实陈述最终行为，并将其保留在最窄的项目 owner 中。 |
| 同一项稳定政策或工作适用于多个仓库 | 共享 | 仅保留跨项目行为；在运行时发现项目事实，把更窄的决定留在本地。 |

删除项目细节并不会让工件变成 Shared。要用可追溯证据支持 Shared 声明，证明其政策或工作不依赖
某一个项目的事实。使用真实 Rule、配置、schema、入口点或已有项目证据；不要仅为了声称可移植性
而虚构完整项目。

Project-local 声明需要会影响行为的当前仓库证据。仅当必须在工作仓库之外演练本地 Rule、配置、文件
或命令时，才使用小型自包含项目。

## 证明行为塑形的必要性

当一项拟议指令的唯一作用是改变 Agent 默认行为，且没有已观察到的失败证明其必要性时，写入前先
运行一次隔离的 Behavior Control。重写时使用先前已接受的工件，新建时不提供候选工件，并让一个
fresh Agent 执行计划用于候选 Acceptance 的同一任务。保留原始结果供 review 使用。

不要为政策权威、项目事实、reference material 或已经观察到的失败运行 control。如果 control 已经
产生要求的行为，则省略这条无作用的指令，除非另有已接受证据要求明确政策。

## 编写运行工件

- 陈述最终政策或工作，而不是编写历史、语义账本、review 流程或 qualification 证据。
- 把项目事实保留在 Project-local 工件中。Shared 工件命名稳定协议，并告诉 Agent 如何发现本地
  事实，或在发现无法得出结果时停止。
- 每项要求只保留在一个 owner 中。遵守更具体的项目 Rule 和受支持的本地 override，但不要将其
  复制到 Shared 文本中。
- 只包含 schema 要求的指令，或无法从可靠加载的 owner 推导且会改变行为的指令。

## 验收代表性使用

在可用时，使用真实政策应用接缝或公开工作入口。所选的 `rule.md` 或 `skill.md` 提供类型专属案例。

把选定案例交给一个隔离的 Acceptance Runner。每个案例都从其声明的冻结输入开始，不要让一个案例
的结果成为另一个案例的输入。像 runtime 一样向 Runner 提供候选工件、代表性任务，以及任务必需的
context 或工具。expected result、semantic ledger、diff、author reasoning、finding 和 prior run output
只供 reviewer 使用。Runner 必须应用工件；学术式解释或 reviewer 的纸面走查不属于 Acceptance 证据。

- 对 Project-local 工件，检查其仓库声明、owner 边界、真实入口或执行点，以及相关本地案例。
- 对 Shared 工件，使用一个有代表性且可追溯的上下文，加上证明政策或工作不依赖项目本地事实的
  直接证据。只有当可移植性声明会实质影响 Acceptance，且直接证据无法证明它时，才增加第二个上下文。
- 通过公开入口运行自有确定性资源。将环境无法运行的受支持执行报告为未测试；受控走查可以说明
  未测试的可执行表面，但不能替代普通工件的隔离应用。

每个案例默认只运行一次。仅当结果不确定或不稳定时，最多使用新的隔离 Runner 重复一次；结果分歧
即失败。当 Readiness 要求 Behavior Control 时，将其原始结果与匹配的候选运行比较，但不要把任何
一方的结果暴露给另一方 Runner。

只有当工件在其声明范围内保持同一含义、对每个选定案例产生一个受支持结果，且不需要臆造项目事实、
动作或出口时，Acceptance 才通过。

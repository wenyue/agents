# 重命名代码

在已批准的兼容边界内，完整重命名一个明确的符号或路径。符号使用语义引用证据，文件或目录使用
精确路径证据。除非用户批准更改，否则保留对外名称。

## 确立重命名

1. 将目标确定为一个符号身份或一个精确仓库路径，并记录当前名称、预期新名称、种类和已批准范围。
2. 阅读目标项目关于命名、生成文件、API 和验证的规则。
3. 对符号，确定其声明，并判断它是私有、公共、用于序列化、由工具生成、持久化、通过反射使用，
   还是被仓库外部使用。对路径，确定其精确当前路径、目标路径、文件系统大小写行为和所有路径引用。
4. 写入前，识别每个生成表面，并证明其源 owner 和重新生成命令。确认目标位置没有标识无关内容，
   且纯大小写路径重命名存在受支持的移动策略。
5. 只有目标身份、预期范围、目标位置归属或公共兼容性决策仍不明确时才询问。

## 确定重命名范围

优先使用理解 import、继承、分派和语言语义的项目级符号或引用工具。如果没有此类工具，将全仓库全词搜索与调用点、类型和配置检查结合使用。

对符号，编辑前对每处匹配进行分类：

- 标识该符号的声明、import、引用、override、测试和文件名；
- 指代同一概念的注释和用户可见文本；
- 基于字符串的反射、注册、route 或动态查找；
- 生成输出及其源头；
- 序列化键、协议字段、数据库列、配置键和其他外部契约；
- 位于其他作用域、与目标无关的同名符号。

只有声明、类型、调用点、配置或其他语义证据能够对应目标时，才把文本匹配纳入本次重命名。

对路径，检查仓库树、版本控制索引、import、manifest、构建文件、测试、脚本、文档链接和区分大小写的
引用。内容搜索没有匹配项，不足以证明路径重命名已经完整。

## 兼容边界

- 有证据表明不存在外部使用方时，完整重命名私有符号和仓库内部符号。
- 对公共 API 或外部契约，如果请求尚未给出兼容性决策，编辑前先说明影响并取得决定。
- 只有确实需要兼容，且项目支持迁移路径时，才添加 deprecated alias。
- 序列化、协议、持久化和配置名称必须保持不变，除非它们明确属于已批准的重命名范围。
- 生成名称通过负责它的源文件修改，再重新生成输出。

## 工作流程

1. 记录已批准的新旧名称映射和兼容策略。
2. 对符号，更新其声明和每处已确认的语义引用。对路径，通过仓库支持的机制把精确源路径移动到
   已批准目标位置，并更新每处已确认的路径引用。直接的纯大小写移动不受支持时，使用唯一中间路径；
   绝不覆盖目标位置。
3. 只有测试、注释、文档或镜像文本确实标识同一目标时，才对其重命名。
4. 从已经确定的源重新生成每个归属明确的输出。
5. 对符号重新执行语义引用发现，对路径重新执行精确路径发现。把每处剩余旧名称归类为有意保留的
   外部契约、无关身份或遗漏的重命名。
6. 运行目标仓库针对受影响表面要求的全部验证，包括适用的格式化、静态分析、生成输出检查和受
   影响测试。
7. 如果重新发现或验证暴露出范围内的漏改，执行一次修正，然后重新运行受影响的发现和全部受影响
   检查。

## 结束本次运行

- **完成**：只有目标已使用批准名称、每处已确认引用都能解析、所有旧名称残留都已分类、生成输出
  为最新状态且全部必需检查通过时，才算完成。
- **写入前停止**：无法证明身份或范围；目标位置冲突或纯大小写移动没有安全策略；会改变未批准的
  公共或外部契约；或无法确定必需的生成源或命令时，写入前停止。
- **写入后失败**：修正后仍有必需检查失败、恢复会扩大范围或改变契约，或已经无法区分本次重命名
  与无关改动时，判定失败。保留有用的部分状态，并报告确切失败检查和下一 owner。

写入后，失败优先于同时发生的停止条件。报告停止事实，不得编造契约、命令或更大的重命名范围。

## 结果

报告被重命名的符号或路径、兼容性结果、受影响表面、有意保留的旧名称、生成输出、执行过的修正、
确切检查及退出状态，以及所有未解决或未测试的表面。

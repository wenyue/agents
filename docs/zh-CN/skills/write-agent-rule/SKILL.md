# 编写 Agent Rule

先应用 `writing-for-agents` 处理通用的 Agent 文档结构、上下文指针、信息层级、相关性和裁剪。本
Skill 负责 Rule 分类、策略边界、强度、范围、分发和生成契约。

产出一项其他 Agent 无需隐藏背景即可应用、前后一致、可执行且有证据支撑的 Rule。在已批准的范围内
重建完整策略，不要沿用旧改动留下的结构。

## 编写标准

清晰、可执行和只有一种无歧义解读是验收条件。满足这些条件后，在不隐藏、合并或删除会改变含义的
信息的前提下，让 Rule 尽可能精简。只要会影响应用，就明确写出主体、范围、条件、强度和结果。没有
当前证据或用户明确批准，不得扩大、缩小、削弱、加强或以其他方式重新解释要求。

## 分类

动笔前，根据分发方式、职责归属和用户要求的产物选择一种类型。

| 判断依据 | 类型 |
| --- | --- |
| 策略由一个仓库维护并直接应用 | 项目本地 Rule |
| 发布出去的 Rule 会在不同仓库中直接应用稳定策略 | 共享 Rule |
| 发布出去的内容负责写出一份由目标项目自己维护的完整 Rule | 共享 Rule 生成契约 |

删掉本地细节并不会自动变成共享 Rule。只有策略本身在不同仓库中保持稳定，才使用共享类型。

## 证据

只收集会改变策略、归属、适用性、分发或验证的证据：

- 定义结果、约束、强度、范围、优先级、例外和明确排除的职责；
- 检查所属 Rule 家族、更宽泛和更具体的 Rule、实际用法、强制执行点、wrapper、registry、manifest、
  镜像和契约测试；
- 对项目本地 Rule，验证应用所需的每项仓库事实、生成内容所有者和模块关系；
- 对共享 Rule，检查有代表性的仓库，只保留稳定的跨仓库策略和受支持的项目本地覆盖；
- 对 Rule 生成契约，检查有代表性的目标 Rule 家族、优先级系统、生成面和 validator。

现有 Rule 只作为证据和遗漏检查使用。可复用过程放在 Skill 中，运行时事实放在其所属配置中，变更
历史不进入最终策略。

## 编写

1. 选择类型，定义完整策略、所有者、强度、范围、适用性、优先级、例外和边界。每个字段都有一个
   明确值，或有经过验证的不适用理由时，本步骤才完成。
2. 根据用户当前意图和已验证证据综合出完整候选版本。保留预期结果、有依据的决定和安全边界；删除
   过时、重复、矛盾、过渡性或放错位置的内容。按照今天重新编写策略的方式组织内容，不要追加说明，
   也不要为了缩小 diff 而沿用旧结构。每项当前要求和有依据的决定都只出现一次时，本步骤才完成。
3. 把每项要求放进负责它的最具体 Rule。只有其他所有者已经在用户要求的范围内时才修改它；否则
   报告依赖并请求批准。每项要求都有且只有一个所有者时，本步骤才完成。
4. 只修改加载或分发所必需的 Rule、wrapper、registry、manifest、镜像、生成输入和契约测试。必要
   表面保持一致且没有修改无关所有者时，本步骤才完成。
5. 根据当前条件和行为编写稳态策略。只有当前输入仍可能触发迁移行为时才保留它，并写明触发条件和
   退役条件。不再含有仅用于记录历史的行为时，本步骤才完成。
6. 使用可观察的条件和结果。除非 Rule 本身是编写顺序会影响结果的生成契约，否则把有序执行过程
   移入 Skill。每项要求都能在不虚构执行过程的情况下应用时，本步骤才完成。
7. 不依赖 diff 阅读完整候选版本。只有解决所有归属、适用性、优先级、例外和强制执行缺口后，才进入
   验证。

受跟踪的 Rule 使用仓库相对路径或稳定的协议自有路径。引用其他 Rule 或 Skill 时使用其规范名称，
除非路径本身属于运行时契约。

## 类型契约

### 项目本地 Rule

根据经过验证的仓库事实说明最终策略。把相关要求和例外保留在负责它们的最具体项目 Rule 中。

### 共享 Rule

只说明稳定的跨仓库策略、语义目标条件、受支持的例外和项目本地优先级。具体实现和更细的项目决定
留在项目侧。

### 共享 Rule 生成契约

将编写流程与它产出的完整目标自有 Rule 分开。定义证据类别和验收条件，不要虚构目标策略。

## 指令形式

- 只有在 Rule 生成契约的编写顺序会影响结果时才使用编号步骤。只对相互独立的策略义务使用
  checklist；每项都写明主体、必要动作或属性，以及可观察结果。
- 只有示例能解决实质歧义时才添加它。示例应保持最小，并在规范性文本中说明每项要求，不要通过示例
  引入策略。
- 优先使用带有可观察条件和结果的正向要求。只有在排除一种合理且有害的捷径时才使用负向要求，并
  同时说明必要替代方案或持续后果。

## Rule 契约

每项最终 Rule 都以下列内容开始：

```markdown
# Rule Title

Strength: `Mandatory|Default|Advisory`

Scope: One sentence naming the Rule's owned responsibility.
```

更宽泛的 Rule 不得重复或静默覆盖更具体的 Rule。只有自有策略需要时才添加 `Boundaries`、
`Exceptions` 或 `Precedence`。生成契约必须让生成证据、完整目标内容、审查、验收和交付各自可发现。

## 验证

### 内容与归属

- 阅读完整 Rule，而不是只看修改行。验证其类型、所有者、强度、范围、适用性、优先级、例外、
  边界和完整策略。
- 确认完整候选版本满足编写标准，并且在裁剪后仍然完整且可执行。
- 确认每项要求和仓库声明都由当前证据支持。
- 确认改动仅限 Rule 的自有表面和已批准的依赖改动。
- 按结构比较语言镜像，并保持路径、命令、标识符、代码块、分类、强度和行为一致。

### 适用性

- 对项目本地 Rule，在当前仓库中验证具体声明、强制执行点、例外和跨 Rule 关系。
- 对共享 Rule，在具有项目本地优先级和受支持覆盖的代表性上下文中执行验证。
- 对生成契约，产出并审查至少一项完整的代表性目标 Rule；当声称广泛可移植性时，使用具有实质差异
  的目标。

### 分发

针对每个修改过的发现或分发面，运行当前 validator、契约测试和 diff 完整性检查。只要证据、策略、
归属或某个必要表面仍未解决或未验证，就不能报告成功。

## 结果

报告 Rule 类型与所有者、最终策略结构、保留的决定、删除或移动的内容、修改的生成与分发面、已批准
的依赖改动，以及准确的验证结果。

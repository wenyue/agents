# 调试模式

你现在处于 **调试模式**——一个以假设驱动的调试工作流。不要直接跳到修复。按顺序完成每个阶段。

---

## 阶段 1：理解问题

如果用户尚未提供，请询问：预期行为与实际行为、复现步骤、错误消息。

阅读相关源代码，理解调用链和数据流。

## 阶段 2：提出假设

以编号列表提出**可验证的假设**：

```
根据我的分析，目前有以下假设：

1. **[标题]** — [可能出错的内容及原因]
2. **[标题]** — [说明]
3. **[标题]** — [说明]
```

同时包含明显与不明显的原因（竞态条件、差一错误、过期闭包、类型强制转换等）。

## 阶段 3：检测代码

### 日志文件

使用绝对路径写入 **`{project_root}/.claude/debug.log`**。

**`project_root` = 硬编码常量字符串**，根据上下文（对话中的文件路径）推断。禁止使用：`import.meta.dir`、`__dirname`、`process.cwd()`、`Deno.cwd()`、`path.resolve()` 或任何运行时检测。例外：远程/CI 环境或本地文件系统不可写时，改用 `/tmp/.claude/debug.log`。

每次复现前：必要时创建 `.claude/`，然后**清空**日志。

服务端：使用文件追加 API（`fs.appendFileSync`、`open("a")` 等）。浏览器端：通过 `fetch` POST 到调试 API 路由。**必须能在所有环境中工作**（开发/发布）。

### 区域标记

所有检测代码都必须包在区域块中，以便彻底清理：

```
// #region DEBUG       (JS/TS/Java/C#/Go/Rust/C/C++)
# #region DEBUG        (Python/Ruby/Shell/YAML)
<!-- #region DEBUG --> (HTML/Vue/Svelte)
-- #region DEBUG       (Lua)

...检测代码...

// #endregion DEBUG    (对应的结束标记)
```

### 日志规则

- **绝不使用 `console.log`、`print` 或任何 stdout/stderr 输出。** 所有调试输出都必须写入 `debug.log`——服务端通过文件追加，浏览器端通过 `fetch` 调用调试 API 端点。
- 日志消息包含假设编号：`[DEBUG H1]`、`[DEBUG H2]` 等。
- 记录变量状态、执行路径、时序和决策点。
- 保持最少——只记录确认或排除每个假设所需的内容。

检测完成后，让用户复现问题，然后**停止并等待**。

## 阶段 4：分析日志并诊断

用户完成复现后：

1. **先检查日志文件大小**（例如 `wc -l` 或 `ls -lh`）。如果日志较大，使用 `tail` 或 `grep "[DEBUG H"` 仅提取相关行，不要读取整个文件，以免淹没上下文窗口。
2. 将日志映射到各个假设——判断哪些假设**已确认**、哪些**已排除**。
3. 用证据给出诊断：

```
## 诊断

**根本原因**：[有日志证据支持的说明]

证据：
- [H1] 已排除 — [原因]
- [H2] 已确认 — [日志证据]
```

如果结论不足：提出新假设 → 增加检测 → 清空日志 → 再让用户复现。

## 阶段 5：生成修复

编写修复，保留调试检测代码。

清空 `.claude/debug.log`，让用户验证修复是否有效，然后**停止并等待**。

## 阶段 6：验证并清理

**如果已修复：** 删除所有 `#region DEBUG` 块及其内容（使用 Grep 查找），删除 `.claude/debug.log`，然后总结。

**如果未修复：** 读取新日志，询问用户观察到的现象，回到**阶段 2**继续迭代。

---

## 规则

- **绝不跳过阶段。** 即使认为已经知道答案，也必须检测并验证。
- **用户确认修复前，绝不删除检测代码。**
- **绝不使用 `console.log`、`print` 等。** 所有调试输出都只能通过文件追加写入 `.claude/debug.log`。
- **每次复现前始终清空日志。**
- **始终使用 `#region DEBUG` 块包裹检测代码。**
- 要求用户复现后，**始终等待用户**。

# 编写 Agent Skill

先应用 `writing-for-agents` 处理通用的 Agent 文档结构、上下文指针、信息层级、相关性、裁剪和 Skill
调用机制。本 Skill 负责 Skill 分类、工作边界、发现、分发、脚本、资源和生成关口。

产出一项其他 Agent 无需隐藏背景即可使用、前后一致、可发现、可执行且有证据支撑的 Skill。在已批准
的范围内重建完整工作，不要沿用旧改动留下的结构。

## 编写标准

清晰、可执行和只有一种无歧义解读是验收条件。满足这些条件后，在不隐藏、合并或删除会改变行为的
信息的前提下，让 Skill 尽可能精简。只要会影响执行，就明确写出执行者、触发条件、输入、条件、动作、
停止与完成条件、失败行为和结果。没有当前证据或用户明确批准，不得扩大、缩小、削弱、加强或以其他
方式重新解释指令。

## 分类

动笔前，根据分发方式、职责归属和用户要求的产物选择一种类型。

| 判断依据 | 类型 |
| --- | --- |
| 整项工作由一个仓库维护并执行 | 项目本地 Skill |
| 发布出去的 Skill 会在不同仓库中执行同一套稳定流程 | 共享 Skill |
| 发布出去的内容负责写出一份由目标项目自己维护的完整 Skill | 共享 Skill 生成契约 |

删掉本地细节并不会自动变成共享 Skill。只有工作流在不同仓库中保持稳定，而且目标项目的具体事实可以
在运行时发现，才使用共享类型。

项目本地 Skill 和共享 Skill 都可以负责操作、诊断或编排。只有这种区分会改变归属、执行方式、关口
或完成条件时，才需要记录。

## 证据

只收集会改变工作、归属、适用性、分发或验证的证据：

- 定义结果、触发条件、输入、约束、开始、完成、停止和失败行为，以及明确排除的职责；
- 检查所属 Skill 目录、资源、脚本、镜像、测试、实际用法、调用方、wrapper、索引、manifest 和其他
  发现或分发入口；
- 对项目本地 Skill，验证执行所需的每项仓库事实和命令；
- 对共享 Skill，检查有代表性的仓库和平台，以及所有必须在运行时发现的目标事实；
- 对 Skill 生成契约，检查一个有代表性的目标，以及编写、审查、验收和交付面。

现有 Skill 只作为证据和遗漏检查使用。项目策略放在 Rule 中，运行时事实放在其所属配置中，变更历史
不进入最终工作。

### 自有表面

只修改执行或分发所必需的 Skill、自有资源、wrapper、索引、manifest、镜像和契约测试。当其他所有者
必须改变时，先报告依赖并取得扩大范围的批准。

受跟踪的 Skill 使用仓库相对路径、Skill 根目录相对路径或稳定的协议自有路径。运行时绝对路径应从
已发现的根目录或任务输入推导。引用其他 Rule 或 Skill 时使用其规范名称，除非路径本身属于运行时
契约。

## 编写

1. 选择类型，定义完整工作、所有者、结果、边界、开始、完成、停止和失败行为。每个字段都有一个明确
   值，或有经过验证的不适用理由时，本步骤才完成。
2. 根据用户当前意图和已验证证据综合出完整候选版本。保留预期结果、有依据的决定和安全边界；删除
   过时、重复、矛盾、过渡性或放错位置的内容和资源。按照今天重新编写 Skill 的方式组织内容，不要
   追加说明，也不要为了缩小 diff 而沿用旧结构。每项当前要求和有依据的决定都只出现一次时，本步骤
   才完成。
3. 把每项要求放进负责它的最具体 Skill 章节或自有资源。只有其他所有者已经在用户要求的范围内时才
   修改它；否则报告依赖并请求批准。每项要求都有且只有一个所有者时，本步骤才完成。
4. 只修改执行或分发所必需的 Skill、自有资源、wrapper、索引、manifest、镜像和契约测试。必要表面
   保持一致且没有修改无关所有者时，本步骤才完成。
5. 根据当前输入、条件、动作和结果编写稳态工作。只有当前输入仍可能触发迁移行为时才保留它，并写明
   触发条件和退役条件。不再含有仅用于记录历史的行为时，本步骤才完成。
6. 使用可观察的条件、动作和结果。当顺序影响正确性或安全性时使用有序步骤，对重复、确定性或脆弱的
   工作使用脚本。每项指令都能在不虚构缺失步骤的情况下执行时，本步骤才完成。
7. 不依赖 diff 阅读完整候选版本。只有解决所有触发、动作、边界、停止、失败、完成、验证和交付缺口
   后，才进入验证。

当 Skill 创建或更新长期 Rule 时，对这项独立产物应用 `write-agent-rule`；只有独立审查通过后，这条
分支才完成。对 Skill 生成契约，分别保留编写、Review Gate、Acceptance Gate 和交付证据；只有两个
关口都记录决定并且交付证据就绪后，这条分支才完成。

## 类型契约

### 项目本地 Skill

- 写入经过验证的仓库事实，并在仓库要求的结果处结束。
- 如果项目已有确定的运行时，自有脚本使用该运行时。
- 可复用过程放在 Skill 中，策略放在项目 Rule 中。

### 共享 Skill

- 用运行时发现、Skill 自有资源、稳定的协议路径和明确停止条件替代项目专用假设。
- 在不同目标上下文中保持同一个受支持结果；不要在不受支持的平台上静默降级。
- 每项 Skill 自有的脚本化工作流都提供成对的 `.sh` 和 `.ps1` 入口。两个入口必须面向同一个结果，
  同时允许已验证的平台差异。

### 共享 Skill 生成契约

- 将编写流程与生成后 Skill 的运行时过程分开。
- 定义目标证据和必须生成的结果，不要虚构目标事实。
- 要求 Review Gate 审查完整候选版本，并要求 Acceptance Gate 在有代表性的目标上下文中执行候选版本。
- 只有两个关口都通过后才交付。交付内容包括候选版本、支撑证据、两个决定，以及未解决或未测试的面。

## 指令形式

- 顺序影响执行时使用编号步骤。只对相互独立的验证、验收或交付条件使用 checklist；每项都写明动作、
  对象和可观察结果。
- 只有示例能解决实质歧义时才添加它。示例应保持最小，并在规范性文本中说明每项要求，不要通过示例
  引入策略。
- 优先使用带有可观察条件和结果的正向要求。只有在排除一种合理且有害的捷径时才使用负向要求，并
  同时说明必要替代方案或持续后果。

## Skill 契约

使用 `writing-for-agents` 定义的发现元数据和调用方式。Skill 名称使用小写连字符格式，不超过 64 个
字符，并与其目录一致。在一个 H1 后紧跟简短的结果和边界段落。让归属、开始、完成、停止、失败、
验证和交付在正文中可发现；只有工作需要时才添加相应章节。

## 自有资源

Skill 只能引用一层深度的自有资源，而且每项引用必须说明何时需要该资源。Skill 自有脚本必须明确依赖、
失败恢复和安全的代表性测试。只有 Skill 会在产物中使用某项资产时才添加它。

除非外部打包契约要求，否则不要添加 README、changelog、安装指南或快速参考。wrapper 只保留平台
元数据和一个源引用。

## 验证

### 内容与归属

- 阅读完整 Skill，而不是只看修改行。验证其类型、所有者、发现元数据、结果、开始、完成、停止、
  失败行为、自有资源、脚本、分发面、镜像、验证、交付和必需关口。
- 确认完整候选版本满足编写标准，并且在裁剪后仍然完整且可执行。
- 确认每项指令、仓库或平台声明和命令都由当前证据支持。
- 确认改动仅限 Skill 的自有表面和已批准的依赖改动。
- 按结构比较语言镜像，并保持路径、命令、标识符、代码块、分类和行为一致。

### 执行与关口

- 使用项目运行时验证项目本地脚本。对于成对的共享入口，运行当前平台入口，并将另一个报告为未运行。
- 对修改过的工作流和自有资源，测试正常完成以及每条相关的停止、失败、明确错误和恢复路径。
- 当声称广泛可移植性时，在具有实质差异的目标上下文中执行共享 Skill。
- 对生成契约，先审查完整生成候选版本，再在有代表性的目标中执行其真实工作流，并分别保留审查和
  验收证据。

### 分发

针对每个修改过的自有资源、发现面或分发面，运行当前 validator、契约测试和 diff 完整性检查。只要
证据、工作、归属、某项自有资源、必要关口或必要表面仍未解决或未验证，就不能报告成功。

## 结果

报告 Skill 类型与所有者、最终工作结构、保留的决定、删除或移动的内容和资源、修改的发现与分发面、
脚本与关口、已批准的依赖改动，以及准确的验证结果。

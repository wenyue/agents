# 项目契约

强度：`Mandatory`

适用范围：生成契约，用于定义目标仓库变更在能力归属、安装、文档、评估、契约演进、分发以及硬性依赖或
暴露边界方面持续有效所必须满足的条件。

## 生成契约

生成由目标项目负责的 `.agents/rules/01-project-contracts.md`，标题为 `Project Contracts`；它应当是
项目本地的普通强制性 Rule，并回答：项目变更必须持续满足哪些条件才能保持有效？

根据仓库当前证据推导目标 Rule 的适用范围与适用条件、可观察的条件到结果映射、例外、优先级和归属边界。
只纳入有依据的政策簇，并选择一个覆盖所有已纳入有效性条件的激活条件组。围绕目标自身的证据组织内容，
不要复制本契约的标题或顺序。

保留现有目标中每项有依据的语义义务，除非已接受的意图和权威的当前证据共同选定对其进行变更或废止。若激活
条件组、适用条件、必需结果、例外、优先级或保留边界仍允许存在实质不同的政策，则在写入目标前停止。

## 条件性证据与选择

阅读现有目标 Rule、其发现入口、更具体的项目 Rule、已接受的规范，以及检验所声明契约的测试。将现有
陈述视为需要保留或质疑的证据，而不是大纲。对每个有依据的政策簇，说明触发事实、可观察结果、确切例外、
优先级和决策责任方。冲突时以适用范围最窄的权威当前责任方为准；必要时引用更具体的政策并保持其优先级，
而不是重复或暗中覆盖它。缺失、冲突、历史遗留或仅在本机成立的证据，不能确立项目政策。

- 追踪公共 API、路由、schema、事件、序列化、领域模型、持久化与迁移行为、状态责任方、生命周期转换、
  取消、并发和清理。只有当这些证据表明某个使用方、状态、兼容性或清理边界决定变更是否持续有效时，
  才纳入相应条件。
- 追踪每项能力从其 canonical registry 或权威来源，经过 synchronizer、renderer、adapter、manifest、catalog，
  直至交付面。当证据明确一个权威来源并约束编辑或交付时，应在必需结果中区分源权威与转换、适配和传输
  职责。
- 检查目标 setup 状态、归属 manifest、确定性 digest、结构化字段组合、接纳和冲突处理，以及移除规划。
  当 setup 声明归属或修改目标内容时，根据这些归属证据定义其声明归属、保留、冲突、替换和废止结果。
- 比较公开文档边界、规范语言源、翻译、运行时加载和交付配置。只有当证据能区分公开材料与面向贡献者的
  材料、规范语言与派生语言，或文档与运行时或交付输入时，才纳入相关政策，并说明所需边界或派生结果。
- 检查 evaluator、fixture、schema、行为测试、已接受的 Standard、任务规范和 verdict 失效行为。当结构与
  自然语言语义需要不同的证明，或治理证据决定哪些既有 verdict 仍然有效时，纳入评估政策；说明证明边界
  和失效结果。
- 追踪实现、文档、测试、验证、持久化状态和调用方中的废止。若移除必须在这些责任方之间保持一致，则纳入
  当前契约政策，并指出证据保留为当前正确性要求的所有兼容或恢复行为。
- 检查 import、调用路径、loader、package 与 plugin manifest、可见性控制和生成分发路径。当违反已核实的
  方向、可见性边界或公开/私有界面会使变更无效时，纳入单向分发以及硬性依赖或暴露政策，并说明必需的
  方向或暴露结果。

## 边界

- 命令发现、setup 机制、同步、修改、测试和验证流程应留在其所属工具与 Skill 中。本 Rule 可以约束这些
  流程的有效结果，但不规定其执行工作流。
- 当 Agent 能够可靠发现文件、目录、命令、配置、schema、registry 和 inventory 事实时，让这些事实继续
  由环境负责。记录持久关系或决策边界，不要缓存这些事实。
- 将建议性的放置原则、职责图和架构启发式规则保留在 `Project Structure` 中；将硬性依赖、分发和暴露
  条件放入本 Rule。

## 验证与交接

根据权威证据验证每项已纳入的映射，包括最接近的纳入与排除情形、归属边界、Rule 冲突、打包、发现机制，
以及受影响且归项目所有的 machine surface。通过当前普通 Rule 流程交接目标，并报告保留的义务、获准的变更、
有证据支持的省略项和尚未解决的界面。
